# CAD View to Code

## 用途

把一个**正在 OpenCAD Studio 里看着的视图**，反向还原成项目原生的 C# 绘图代码。
关键词是"还原"而不是"抄坐标"：几何、图层、块语义、重复规律都要在代码里重建，并且能被验证。

## 产物模型

**一张图纸 = 一个工作区 = 一个 .cs 文件**。图纸可以有很多地方要看，所以要抓很多张图：

```text
artifacts/<drawing>/                     ← 一张图纸，一个工作区
├─ shot-01/                              ← 第 1 张截图（一个视口/一个局部）
│  ├─ view.png                           ← 截图原图（全景）
│  ├─ view.json                          ← pixel→world 矩阵、camera_revision
│  ├─ regions.json                       ← 分区结果（像素框 + 世界框）
│  ├─ view-regions.png                   ← 红框图：每个区域一个红框 + 编号
│  ├─ view-regions-final.png             ← 剔空区后的红框图（灰框=空区）
│  ├─ region-01-detail.png …             ← 每个区域放大后的细部图
│  └─ details.json                       ← 每张细部图的世界框、矩阵、mm/px
├─ shot-02/ …                            ← 第 2 张截图，结构同上
├─ regions/                              ← 全部区域 JSON 平铺在一处
│  ├─ shot-01-region-01.json
│  ├─ shot-01-region-02.json
│  ├─ shot-02-region-01.json
│  └─ index.json                         ← 汇总：每张截图有哪些区域、对应哪个方法
├─ baseline/                             ← 可选：--strict 1:1 基线，只作对照，不交付
└─ MyDrawing.cs                          ← 一个图纸只有一个 .cs（在 CadCli 里）
```

对应关系是**逐级确定**的：

| 层 | 数量 | 命名 |
|---|---|---|
| 图纸 | 1 | `<drawing>` 工作区目录 |
| 截图 | N | `shot-01/`、`shot-02/` … |
| 红框图 | 每张截图 1 张 | `shot-NN/view-regions.png` |
| 细部图 | 每个区域 1 张 | `shot-NN/region-MM-detail.png`（相机推到该区域） |
| 区域 JSON | 每张截图 M 个 | `shot-NN-region-MM.json`（**截图号 + 红框号**） |
| C# 文件 | **整个图纸 1 个** | 追加写入，不按截图拆文件 |
| C# 方法 | 每个 JSON 1 个 | 单截图 `DrawRegionMM`；多截图 `DrawShotNNRegionMM` |

为什么方法名要分支：只有一张截图时 `DrawRegion01…03` 最自然（现有两个类就是这个命名）；
一旦有第二张截图，两个截图都会有自己的"区域 1"，不加截图前缀就撞名了。所以**多截图时全部加前缀**，
命名规则随截图数自动切换，`index.json` 里记着每个区域最终叫什么。

## 两个阶段

这条链路分成两段，**第一段求"对"，第二段求"好"**。两段都从同一份 JSON 出发，
所以优化前后的差异是一份可复现的 diff，而不是"重写了一遍"。

```text
第一部分：还原（faithful）—— 每张截图走一遍
  当前视图 ──capture──> shot-NN/view.png + view.json（pixel→world 矩阵）
          ──segment──> shot-NN/regions.json + view-regions.png（红框标出每个区域）
          ──确认────> 红框图发给用户，用户明确同意后才继续（硬闸门，见 §2.1）
          ──kind────> 每区定性 table / rebar_detail / title / plan / notes（第二个硬闸门，见 §2.2）
  ──export───> regions/shot-NN-region-MM.json（detail=full，剔除空区，写入 kind）
                        └ shot-NN/view-regions-final.png（红框=有效区，灰框=空区）
          ──detail──> shot-NN/region-MM-detail.png（相机推到区域，细部图）
          ──check────> 把 JSON 坐标投影回细部图验证对位（脱节即 0%）
          ──gen --strict──> 追加进同一个 .cs（一条源线段一条语句，一个区域一个方法）

第二部分：优化（idiomatic）—— 仍是同一批 JSON
  同一份 JSON + DwgSharpKit + 上一步的 C#，按 kind 分派转换器
          ──merge───> 同 x/同 y 的共线重叠段先并段，再把端点 ≤0.5 mm 的线/弧串成多段线
          ──map─────> HRB400 / 钢筋断面 / 双筋 / _Oblique → 项目块替身
          ──rebar───> rebar_detail 区：一根钢筋 → Stirrup（闭合+双钩）或 Rebar（开放折线）
          ──array───> 等距族折叠成 CadDraw.EntityArray
          ──table───> 规整网格整体转成 TableHelper.CreateTable 的 TABLE
          ──verify──> 生成的 DWG 与源图四项对齐
```

**为什么分两段**：合并、阵列、表格化都会改变"实体个数"，一旦出问题就很难判断是映射错了还是优化错了。
先有一份 1:1 的基线，任何偏差都能回退到基线做对照——这是这个 skill 和"让模型一把梭"最大的区别。

```powershell
# 第一部分：基线（不合并、不阵列、不转表格）——写到 artifacts 下，不要写进交付目录
python scripts/json_to_csharp.py artifacts/pier/regions `
    --class MyDrawingBaseline --strict --out artifacts/pier/baseline/MyDrawingBaseline.cs

# 第二部分：优化版（默认行为）
python scripts/json_to_csharp.py artifacts/pier/regions `
    --class MyDrawing --out path/to/Drawing.cs
```

**路径约定**：`scripts/…` 相对**本 skill 目录**（脚本就在 SKILL.md 旁边）；
`artifacts/<drawing>/…`、`--out`、`--class` 里的类名都相对**当前项目目录**。
生成器只依赖标准库；`check` 子命令额外用 Pillow + numpy。

追加进已有文件的写法（一张图纸只有一个 .cs，第二张截图起就靠它）：

```powershell
python scripts/json_to_csharp.py artifacts/pier/regions `
    --class MyDrawing --out path/to/Drawing.cs --append
```

`--append` 是**并进已有类**：同名方法原地替换，新方法插到类尾，不会另起一个类。
所以第二张截图抓完、导出完，重跑一次这条命令就够——类里方法数自动跟着 JSON 数量走。
类名不在文件里时（第一次写、或换了类名）才退回"追加一个新类"。

## 何时使用

- "把当前视图里的图用代码实现一遍"、"照着这张图生成 C# 绘图代码"；
- 给出截图/分区，要求每区一个 JSON、一个 JSON 一个函数；
- 需要在一块新图纸上重复"截图 → 分区 → JSON → C# → 优化 → 校验"。

不适用：只解析 JSON 语义（用 `cad-rebar-skill` 的三区联动），或只修一条线。

## 核心不变量

1. **一个区域 JSON = 一个 C# 方法**，方法之间不共享临时变量，不额外出"工具函数"。
2. **坐标保留源图绝对坐标**，不做整体平移，生成的 DWG 才能和源图直接叠。
3. **几何等价可验证**：实体数、类型分布、图层分布、包围盒四项对齐，才允许说"还原成功"。
4. 合并只在**同图层**内做；跨图层合并会改变显示规则，一律禁止。
5. 优化只允许做**可逆的等价变形**：合并/阵列/表格化都不能改变图面几何；
   改变实体类型的优化（表格化）必须留下回退路径和说明。
6. **分区必先定性**：每个红框在 `export` 前标一个 `kind`（`table` / `rebar_detail` / `title` /
   `plan` / `notes`），混了多类的标 `mixed` 并回 §2.1 再拆。**走哪条转换器由 `kind` 决定**，
   判错比不还原更糟——表格判成大样会生成一张"好看但几何全错"的图。
7. **钢筋长度只取标注，不取几何**：大样图是示意画法（实测 N3-1 画 7151.63、实为 9076）。
   每根必须满足 `Σ段标注 + 弯钩 = 引线 L`，否则一律视为读错，回去重读。

## 阶段 0：先侦察仓库

生成前必须读：目标 C# 文件与相邻生成类（命名空间、命名、`using`）、`DwgSharpKit` 的
`CadDraw` 各 partial / `CadArray` / 块帮助器（`HRB400Block`、`SteelSection`）/ **`Tables.TableHelper`** /
**`Rebar` 家族**（`Rebar`、`RebarDetail`、`SymmetricRebar`、`AsymmetricRebar`、`Stirrup`、`RebarXData`）、
`CadLayers` 常量、以及入口 `Program.cs` 与 `GeneratedDraw.*`（确认怎么建文档、怎么存 DWG、有没有 `--stats` 反查）。

**现有 API 是权威**，先 grep 到签名再写。

## 第一部分：还原

### 1. 抓当前视图（一张截图）

```powershell
python scripts/ocs_regions.py --drawing pier capture --shot 1
```

`--drawing` 是图纸工作区名，`--shot` 是截图号，产物落到 `artifacts/pier/shot-01/`：
`view.png` + `view.json`。矩阵是六元组 `[a,b,c,d,e,f]`，`wx = a*px + c*py + e`，`wy = b*px + d*py + f`；
`d` 为负（屏幕 y 向下、世界 y 向上），像素框转世界框后要重新求 min/max。细节见
[references/ocstudio-mcp.md](references/ocstudio-mcp.md)。

**图纸要分几处看就抓几张**：把视口滚到 A 处 `capture --shot 1`，滚到 B 处 `capture --shot 2`，
依次往下。编号只增不重用，重抓同一处就覆盖同一个 `--shot`。

### 2. 分区并**画红框**

```powershell
python scripts/ocs_regions.py --drawing pier segment --shot 1
```

墨迹投影：灰度 > 60 算墨迹（CAD 常是黑底白线，要用亮像素）→ 列带（间距 < `--gap-x` 合并）→
每列带内行带（间距 < `--gap-y` 合并）→ 交集为区域。

同时输出 `shot-01/view-regions.png`：在原截图上用**红框**圈出每个区域并编号 `1…N`。
这一步不是装饰——分区参数合不合适、有没有把两类内容框进同一个区域、边缘的界面元素有没有被误当内容，
只有把框画回去才看得见。**不要只报数字就往下走。每张截图都有自己的红框图，逐张核对。**

### 2.1 确认闸门：先把红框图给用户看（必须停）

分区是整条链路里唯一"用户一眼就能判断对错"的环节，框错了后面 export / detail / gen 全白做。
所以这里**是硬停点，不是建议**：

1. 把 `shot-NN/view-regions.png`（改过分区就用最终版）**作为图片发给用户**，附一张小表：
   区域号、内容、实体数、尺寸；
2. 明确问一句："分区是否可行？有没有该合并/该拆开的地方？"
3. **拿到用户明确同意**（"可以 / 没问题 / 继续"）才执行第 3 步 `export`；
4. 用户说"再细分 / 这两块该合 / 漏了一块"→ 调 `--gap-x/--gap-y` 或手工分区 → 重画红框图 →
   **回到第 1 条重新确认**；
5. 用户没回复就停在这里等，不许"先把代码生成了再说"。

> 大区域（一个框里塞了好几个视图/表格）最适合在这一步拆：拆成按视图的子区后，每个子区的细部图 mm/px
> 才够看清字。拆完仍要让用户看新红框图，不要默默往下走。

### 2.2 分区定性：先搞清"这个框画的是什么"（第二个闸门）

分区确认之后、`export` 之前，必须给每个区定一个 `kind`。这是**第二个硬停点**，理由和 §2.1 一样硬：
**`kind` 决定走哪个转换器**，判错会产出一张"看起来像、几何全错"的图，比不还原更难查。

先脚本算指纹，再让人裁决：

| kind | 指纹（都能在 JSON 上算） | 转换器 |
|---|---|---|
| `table` | 横线按 y 聚类 ≥3、竖线按 x 聚类 ≥2，交点覆盖率 > 0.5，文本都落在格子里 | `detect_tables` → `TableHelper`（§10） |
| `rebar_detail` | 主体是若干 2~8 顶点多段线 + 大量短数字/带 `H±`、`R` 前缀的文本 + 多个 `HRB400` 引线块 | `Stirrup` / `Rebar`（§7.3） |
| `title` | 已有 `TitleBlock` 判据 | `TitleBlock.Add`（§7.1） |
| `plan` / `elevation` | 线密集 + `钢筋断面` 块 + 尺寸标注 | 线/弧合并 + 阵列（§6~§9） |
| `notes` | 几乎全是 `MText` | 逐条 `CadDraw.MText` |
| `mixed` | 上面几类都有 | **不许进 export**，回 §2.1 再拆 |

写回区域 JSON 与 `index.json`：

```json
{ "kind": "rebar_detail", "kind_label": "钢筋大样图",
  "kind_evidence": {"polylines": 16, "leaders": 14, "texts": 83},
  "kind_source": "user-confirmed" }
```

`index.json` 里同样记 `kind`，这样"红框 ↔ JSON ↔ 方法 ↔ 转换器"四者能对上。

**闸门呈现**：把 `区号 / kind / 判定依据 / 转换器` 列成一张小表发给用户确认。
`mixed` 是唯一能在这一步改分区的信号——拆完要重新走 §2.1 的红框确认，不要跳过。

> 指纹只是把判断变成可核对的东西，不替代判断。看图仍然第一位：
> 一个框里有 14 个 `HRB400` 引线块，那就是 14 根钢筋，这比任何几何指纹都直接。

### 3. 导出 JSON 并剔除空区

```powershell
python scripts/ocs_regions.py --drawing pier export --shot 1
```

每区一次 `ocs_read query`（`detail: "full"`，参数必须嵌在 `parameters` 下），分页拉全。
**只导出模型空间实体**：`ocs_read query` 会把尺寸匿名块（`*D…`）里的图形缓存一并返回——
标注文字（MText/Text）、箭头块 `_Oblique`、尺寸线与界线、Defpoints 点。它们的 `owner_handle`
不是 `*Model_Space`，若原样落盘，生成器会既画原生 DIMENSION 又画一遍这些缓存，图面出现重影
（典型症状：同一条 `a`/`mx150`/`128` 既在 `RotatedDimension` 里、又有一条 `CadDraw.Text/MText`）。
`export` 现在按 `owner_handle` 过滤：只保留模型空间实体（Dimension 取
`properties.<kind>.base.common.owner_handle`），过滤数写进区域 JSON 的 `filtered_block_entities`。
需要旧行为（连同块内缓存一起导出）时加 `--keep-block-entities`；布局不是 Model 时自动跳过过滤。
导出后剔除**空区**：视图边缘的视图立方、命令行条也是墨迹，但查询返回 0 实体。
剔除后重编号，文件名为 `shot-NN-region-MM.json`（截断号 + 红框号），并把结果画成
`shot-01/view-regions-final.png`：保留区红框+新编号（与 JSON 文件名一一对应），丢弃区灰框标「空」。
这张图就是"红框 ↔ JSON ↔ 方法"的对照表。

所有截图的 JSON 都平铺在 `artifacts/pier/regions/`，`index.json` 汇总每张截图有几个区、各叫什么方法。

JSON 结构：

```json
{ "drawing": "pier", "shot": 1, "region_id": 1,
  "kind": "rebar_detail", "kind_label": "钢筋大样图",
  "pixel_box": [0,135,1094,561], "world_box": [...],
  "world_size_mm": [32720.0, 13130.0], "entity_count": 418, "entities": [ ... ] }
```

### 4. 放大抓细部图，并做对位自检

分区图是"全图视角"：一个区域几百个像素，格子里的字只有十几个像素，根本认不出。
把相机推到每个区域再抓一张，同时得到一张大图和**它自己的**坐标矩阵：

```powershell
python scripts/ocs_regions.py --drawing pier detail --shot 1
python scripts/ocs_regions.py --drawing pier check  --shot 1
```

`detail` 对每个区域调一次 `ocs_capture`（`view: "region"` + 该区域的 `world_box`，`max_dimension` 默认 2048），
产物是 `shot-01/region-NN-detail.png` 和 `shot-01/details.json`（记录每张图的世界框与矩阵）。
抓完会把视图复原到原范围，别把画布留在放大状态。

看 `mm/px` 就知道这张图够不够用：`跨度 ÷ 像素`。例：6.7 m 的区域在 1920 px 上是 3.6 mm/px，
250 mm 高的字约 68 px，数字能看清；而全图视角下同一个字只有 8 px。
判据是 **字高 ÷ mm/px ≥ 20 px**。大区域（几十米）即使抓 2048 px 也只有 20+ mm/px，
这时要么把 `--max-dimension` 提到 4096，要么对该区域再切一次子块（局部二次分区）。

**"看图"分两种能力**：

- **有人眼（或图像模型）**：直接看 `region-NN-detail.png`，和 JSON 并排比对——最直接的核对。
- **纯文本模型**：用 `check` 做**可执行的对位检查**——把 JSON 里的坐标用细部图矩阵投影回像素，
  沿每条线采样 9 个点、每点看 ±2 px 内有没有墨迹；文字按字高开窗查笔画。

```text
区域    线命中           文字命中          墨迹占比
1     859/862 (100%)  211/212 (100%)  3.702%
2     24/24 (100%)    107/107 (100%)  3.480%
```

`check` 验的是**对位**，不是字形。它最擅长抓一类致命错误：**JSON 和当前图纸已经脱节**
——图纸被移动/编辑、或忘了重抓，命中率直接掉到 0%。这种情况不要继续生成代码，
先重跑 `capture → segment → export → detail → check`。

> 单独跑 `check` 几乎零成本，却能把"坐标早就过期、代码画到空白处"挡在生成之前。
> 图纸有任何改动（哪怕只是平移），都要重跑。

### 5. 生成 1:1 基线（临时对照，不进代码树）

`--strict`：不合并、不阵列、不转表格，一条源线段一条语句，块仍然按替身映射（那是映射不是优化）。

基线只用来做对照（语句数、映射有没有漏项、优化前后差多少），**不是交付物**，也不要放进
`CadCli/Generated/`——交付目录里出现一个没人引用的 `*Baseline.cs`，用户只会问"为什么有两份？以哪份为准？"

```powershell
# 基线落在 artifacts 下，和分区 JSON 放一起备查
python scripts/json_to_csharp.py artifacts/pier/regions `
    --class MyDrawingBaseline --strict --out artifacts/pier/baseline/MyDrawingBaseline.cs
```

要让基线参与编译（确认它真的能跑），临时拷进项目、build 完立刻删：

```powershell
Copy-Item artifacts/pier/baseline/MyDrawingBaseline.cs CadCli/Generated/_baseline_tmp.cs
dotnet build
Remove-Item CadCli/Generated/_baseline_tmp.cs      # 不要留在仓库里
```

一张图纸的所有截图跑完后，应该得到**一个类、N 个方法**——方法数与 JSON 数一致，不多不少。

### 5.1 标注处理：分列表 → 按 rotation 分组 → 检查尺寸链

每个区域按以下顺序整理标注；基线执行前两步，优化版再执行第三步：

1. **先分开添加**：普通图元放 `List<Entity> entities`，原生标注放
   `List<Entity> dimensionEntities`；方法末尾依次调用 `doc.AddEntities(entities)`、
   `doc.AddEntities(dimensionEntities)`。按实体类型分类，文字仍在普通列表；无标注的区域只建普通列表。
2. **再按 `rotation` 分组**：在 `dimensionEntities` 内把同角度的 `RotatedDimension`
   放在一起，写明角度注释；`0`、`Math.PI / 2`、`Math.PI` 分属不同组，保留源角度和属性。
3. **最后检查同组的连续标注**：`textMiddlePoint` 共享尺寸线法向坐标时列为候选
   （水平比较 Y、竖直比较 X，斜向比较法向投影）；测量点真实首尾相接、尺寸线与样式兼容、
   所有源属性可保持时，才替换成 `..CadDraw.ChainDimension(...)`。不能表达的段保留
   `RotatedDimension`，不能移动源点凑链，也不能跨 rotation 组合并。

含标注的区域必须读取[标注详细规则与方法骨架](references/json-to-csharp.md#21-标注处理固定顺序)。
先确认当前项目 `ChainDimension` 重载，保留每段原生 DIMENSION、源句柄和文字位置；
尺寸链合并不减少标注实体数，不顺便删除重合标注，不套用普通线段的 0.5 mm 拼接容差。
生成脚本输出是初稿；生成或 `--append` 替换方法后，仍须对照 JSON 完成本节整理，不能假定脚本已自动完成。

## 第二部分：优化

### 6. 合并多段线

同图层内端点距离 ≤ 0.5 mm 视为相连；Line / LwPolyline / Arc 统一成带 bulge 的顶点链，
按"节点图"走链（不能按数组顺序两两连）：端点与岔口（度数 ≠ 2）出发，走到另一个非 2 度节点或闭合。

四个已知坑，以及实体级去重、文字 helper 和原生标注的生成规则（详见 [references/json-to-csharp.md](references/json-to-csharp.md)）：
大半径弧不能用圆心判归属（R=25250 时圆心在图形外）；走链起止节点取错会造出假弦；
bulge 至少 6 位小数；闭环必须置 `closed`。

#### 6.0 先做共线并段（同 x / 同 y 的区间并）

尺寸界线这类对象在源图里常被拆成**好几段、彼此还重叠**：一条长竖线，加上每道尺寸线处
一段 50 mm 的出头线，在同一 x 上写 6 条 `CadDraw.Line`，看图是同一块墨迹。

走链合并救不了它——出头线让节点度数变成 3，按"度数 ≠ 2 就断"的规则，长线反而被打断。
所以**在走链之前**先按"同图层 + 同 x（竖线）/ 同 y（横线）"分组，把区间做并：

```text
x=-62161.487 上的 6 段：
  [-19650,-19528] [-19650,-19600] [-19906,-19956] [-19906,-19650] [-20028,-19906] [-21628,-20028]
并后：[-21628,-19528]  →  1 条 CadDraw.Line
```

规则：

- 只并 `kind=="line"`、无 bulge 的两点直线；多段线/弧的顶点链不能按区间并；
- 按 `(图层, 轴向, 固定坐标, 线宽, 标高)` 分组，固定坐标用两位小数聚类、输出仍用原坐标；
- 区间相接或重叠（间隙 ≤ 0.5 mm，与走链同容差）就取并集，被包含的段直接吸收；
- 并完再走链，顶点更少，也更容易落进第 8 步的等距阵列。

实测 04 顶帽图：1147 条 `Line` → 并掉 139 条，语句总数再降 72（1163 → 1091），
`x=-62161.487` 那组 6 条正是并成 1 条。

**验收口径要跟着改**：并段会吃掉"内部的断点"，所以不能再用"源顶点必须在 DWG 顶点集合里"判定，
改成**"源几何顶点必须落在 DWG 的某条线段上"**（点到线段距离 ≤ 0.05 mm）。骨架点没丢、墨迹不变，
这才是等价变形。

### 6.1 去重（并段之前先做）

**判据**：同图层 + 同几何 = 重复对象。源图里同一根线被画了两遍，句柄不同、坐标差 1e-7 mm，
图面上完全重合——留一份就够。逐字重复的 C# 语句（`CadDraw.Line(...)` 连着两行一模一样）就是这个。

两轮，缺一不可：

1. **实体级**：比较"看得见的东西"——类型、**映射后的图层**、几何（坐标四舍五入到 0.001 mm）、外观属性；
   句柄 / 属主 / 扩展数据一律忽略。
   - 图层必须用**映射后**的 `Bxx`：源图「标注」和「B-03 标注」是两个层，映射后同为 `b03`，
     同一根线画在这两个层上，输出会得到两句完全相同的 `CadDraw.Line(..., b03)`。
   - 直线的 `start/end` 先按坐标排序再比较：同一根线正着画、反着画，几何上完全重合，
     不排序就永远判不成重复（`_dedup_key` 里已做）。
   - 闭合多段线比较整个顶点环；起点轮换与方向反转都应得到同一个键。反转时同步反转 bulge、交换起止宽度，并忽略 `vertex_id`。
     不要只根据两条等长或平行边判重。
2. **语句级**：不同来源可能落到同一句——`_Oblique` 块展开的 45° 斜线与同位置的 Line 实体、
   钢筋断面与轮廓线，最终都是同一句 `CadDraw.Line(...)`。按**最终语句文本**收口才彻底。

去重必须在**合并之前**做（重复的线进合并器会造出退化闭环），语句级那一轮则在生成语句之后。

每轮都记录实体级与语句级去重数量；普通图元去重后的完整 C# 语句应没有重复项。多段线调用的开头相同不算重复语句，需比较整个语句。
原生 `Dimension` 不参与这两轮通用去重；保留源标注时，重合标注也各自保留。用户明确要求标注去重时另行判断并记录，不能混入尺寸链合并。

> 去重只删"完全重合"的对象，不会碰"看起来像"的。差值 ≤ 0.5 mm 的两根线不会被当成重复——
> 那是合并的活，两者判定容差不同，不要混用。

#### 7.1 图题：整段交给 TitleBlock.Add

图题不是"几条线 + 几个字"，而是项目的标准块：标题文字 + 上下两条横线 + 比例文字。
识别出这个组合后**整段替换成一次 `TitleBlock.Add`**：

```csharp
..TitleBlock.Add(doc, "正面钢筋布置图", "1:50", CadDraw.P(-58794.903, -18271.186), 50),
```

判据（全部来自 TitleBlock 自己的布局，容差按标题字高 H 取）：

- 标题字高 H ≥ 100、≤ 14 个字、不以 `\` 开头（排除尺寸文字 `\A1;…` 和长附注）；
- 标题下方有**两条平行横线**：长度差 ≤ 15%、上下间距 0.10H~0.50H、中心对中差 ≤ 0.5H；
- 比例文字 `1:xx` 在下横线右端外侧（0~4H、±0.5H 内）；
- `scale = H / 5`（TitleBlock 标题字高固定 5），插入点 = **下横线中点**。

实测 04 顶帽图识别 8 个图题（正面/侧面/半Ⅲ-Ⅲ/半Ⅳ-Ⅳ/Ⅴ-Ⅴ/钢筋大样图/箍筋关系示意图/数量表），
5 个带比例、3 个不带（传空串；`TitleBlock` 已改成空比例不再生成空 Text）。

**这是"标准块重绘"，不是逐像素复制**：源图横线长 = 标题宽 + 小余量，标准块 = 5×字数 + 4 单位，
差距最大约 20%（半Ⅲ-Ⅲ截面 1406 → 1700 mm，出图约 5.9 mm）；上线位置差 3.6 mm、比例文字右移约 65 mm。
验收时把图题区单独归类，不算进"顶点全覆盖"的失败项。

#### 7.2 剖面符号：几何对得上才替换

`SectionBlock.Add(doc, distance, text, insertPoint, direction, scale)` 是固定模板：
剖面线 5 单位、箭头杆 5 单位、箭头 2 单位（偏 15°）、文字 2.5 单位、文字偏移 (3.015, 2.283)。

04 图的 Ⅲ/Ⅳ/Ⅴ/Ⅰ 是**手绘**的：两臂从角点出发、长 194 / 195、箭头 61、文字高 175——
按文字高反推 scale=70，剖面线会被画成 350；按臂长反推 scale=38.8，文字又只剩 97。
比例对不上，硬套会把符号画成另一个样子，所以**保持原样**，并在汇报里写明
"识别到剖面符号，但比例与 SectionBlock 模板不符，未替换"。

判据：找到一对同字文本，各带一条"角点 + 两臂 + 箭头"的折线，且每段长度、文字偏移与模板
在 1 mm 内一致，才替换。**宁可保留手绘，也不要换成一个看起来不对的标准符号。**

#### 7.3 钢筋大样：一个分区 → N 根 → 一根一段

大样区的结构是固定的：**若干根钢筋，每根 = 本体 + 段标注 + 一个 `HRB400` 引线块**。
粒度三层：分区 → 一个方法；一根钢筋 → 方法里的一段；本体/弯钩 → 模型对象。

**数根数按引线块数，不按多段线数。** 引线块是唯一带 `编号` 属性的对象，多段线/直线/文字都没有身份。
同名编号会跨图纸重复——实测同一张 DWG 里 `N3-1` 有 30 多个，**只有先框定分区范围才不会混**。

每根走三步：

1. **认领**：以引线块位置为锚，本体取包围盒最近的多段线（实测 290~380 mm），
   弯钩取落在本体包围盒外扩 400 mm 内的直线，段标注取同范围内的 `Text`。
   这条"外扩 400 mm 归属"同时就是**邻区对象过滤器**：不满足就属于旁边那根，别拿。
2. **放大确认**：只框这一根的句柄，`字高 ÷ mm/px ≥ 20` 才算看得清（实测 N3-1 落到 3.784 mm/px、33 px）。
3. **判型生成**：

| 源图 | 判据 | 用哪个模型 |
|---|---|---|
| **箍筋** | 本体 `closed=true` + **两条独立直线**（弯钩） | `Stirrup`：`Vertices` + `Hooks` |
| **线筋** | 一条开放折线（可带 bulge 弧） | `Rebar`：`Vertices`（段标注挂在段起点） |

| 源图 | 目标 |
|---|---|
| 闭合本体顶点 | `Stirrup.Vertices`，**不重复首点**；**末顶点 `Text` 标闭合段** |
| 开放折线顶点 | `Rebar.Vertices`，每段 `Text` 挂在段起点；末点 `Text` 被忽略 |
| 圆角 | 顶点 `bulge`（90° 圆角 = `-tan22.5° = -0.41421356`），`Perimeter()` 按弧长算 |
| 两条弯钩 | `new StirrupHook(Root, Tip, Text)`；**只给第一条 `Text`**，图面两个钩只标一次 |
| 段标注 | `Text` = **替代长度**，不是几何长度 |
| 引线块 | `HRB400Block.Insert(doc, p, 编号, "{直径} L={长度}", 5)`，事后 `Layer = b04` |
| 整根长度 | `TrueLength = Σ段标注`；带"(平均)"的另给 `SubstituteLength` |

**长度只能取标注，不能取几何。** 大样是示意画法，实测：N3-1 几何 7151.63、真实 9076；
N4-1 几何 2792.74、真实 2986；N4-2 几何与 N4-1 完全相同、真实却是 3382。
用 `GeometryLength()` 会静默算错，而且同形状的几根错得一模一样，肉眼查不出来。

**每根都做长度闭合校验**：`Σ段标注 + 弯钩 = 引线 L`。实测全部闭合：

```text
N3-1  2704+1704+2704+1704+130+130               = 9076  ✅ 关闭箍筋，画 1653×1700
N4-1  141+2704+141                              = 2986  ✅ 开放折线，画 2792.74
N5-1  141+2104+141                              = 2386  ✅
N2-1  239+1800+880+311+239+880+311+1664+130+130 = 6584  ✅ 8 顶点闭合环 + 两处 R150 圆角
```

**大样区取景有自己的坑**：带大半径弧的多段线（矢高 50 mm、R≈50664）会让 `view_focus` 把视野
撑到 71 米。多根取景一律"顶点自己算框 + `ocs_capture view:'region'`"，单根才用 `view_focus` 框句柄。

一个方法的样子：

```csharp
public static void DrawRebarDetail(CadDocument doc)
{
    var options = new RebarDetailOptions
    {
        TextHeight = 125, TextOffset = 120,
        RebarLayer = doc.Layer(CadLayers.B01), TextLayer = doc.Layer(CadLayers.B07),
    };

    // N3-1：Φ14 闭合箍筋，画 1652.98×1700，标 2704×1704，两端各 130 弯钩
    var n31 = new Stirrup
    {
        Number = "N3-1", Grade = "HRB400", Diameter = 14,
        TrueLength = 9076,
        Vertices =
        [
            RebarDetail.V(   0.000,     0.000, "2704"),   // 顶边
            RebarDetail.V(1652.980,     0.000, "1704"),   // 右边
            RebarDetail.V(1652.980, -1700.000, "2704"),   // 底边
            RebarDetail.V(   0.000, -1700.000, "1704"),   // 左边（闭合段）
        ],
        Hooks =
        [
            new(new XY( 587.070,   0.000), new XY( 436.194, -163.986), "130"),
            new(new XY(1652.980, -54.346), new XY(1502.104, -218.332)),   // 第二个钩不重复标
        ],
    };
    doc.AddEntities(n31.Detail(doc, CadDraw.P(-80333.12042378323, 16256.163477335744), options));
    doc.AddEntities([HRB400Block.Insert(doc, CadDraw.P(-79696.83051901542, 16635.631257456298),
                                        "N3-1", "14 L=9076", 5)]);

    // …N2-1、N2-2、N4-1、N4-2、N5-1、N5-2 同法，一根一段

```

`Count`（根数）不在大样区：它在数量表区，用 `编号` 对上。大样给 `编号/直径/长度`，
数量表给 `根数/总长/单位重`，两边合起来才是完整的一根钢筋——这也是 `RebarXData` 值得写的原因。

实测基线：一片大样区 **14 根**（N1-1~N1-6、N2-1/N2-2、N3-1/N3-2、N4-1/N4-2、N5-1/N5-2），
16 条本体多段线里 4 条 `closed=true`（N2-1/N2-2/N3-1/N3-2 一类），其余是开放折线。

### 8. 等距阵列（同 x 或同 y 就是"循环"）

同键（线的向量 / 多段线顶点序列+bulge / 圆半径 / 文字内容+字高 / 断面缩放+旋转）+ 常量步长，
**分行、列、斜向**各扫一遍再贪心取大族，成员数 ≥ 4（文字/断面/多段线 ≥ 3）→
`..CadDraw.EntityArray(模板, CadDraw.P(dx,dy), n)`。

三个方向是同一套代码，步长向量长什么样就怎么循环：

| 源对象的差别 | 步长 | 生成 |
|---|---|---|
| 只有 y 变（x 相同） | `CadDraw.P(0, dy)` | 竖向循环 |
| 只有 x 变（y 相同） | `CadDraw.P(dx, 0)` | 横向循环 |
| x、y 一起变 | `CadDraw.P(dx, dy)` | 斜向循环 |

`key` 是**平移无关**的（线用 `dx,dy`，多段线用相对首顶点的顶点序列，文字用内容+字高），
所以"同一个对象挪到别处"必然同键；锚点单独存，用来算步长。

当前视图实测：51 个阵列 = 横向 24 + 纵向 27 + 斜向 0——说明这批图里的重复结构几乎全是正交排列。
成员数门槛不能再降：2 个成员写成阵列反而更长，3 个才刚打平，4 个以上才明显省。

不阵列的：`HRB400`（属性逐块不同）、`钢筋轮廓（双筋）`（一次出两个实体）。

### 8.1 不等距的同线形：点列表循环

`EntityArray` 只认**常量步长**，可真实图纸里更多是"同一条线、位置不等距"：
8 条 262.5 mm 的竖向尺寸界线，x 间距是 134 / 194 / 194 / …；4 条 300 mm 的横向尺寸线，
y 间距是 256 / 122 / 1600。逐条写 8 句、4 句，模板重复了 8 遍、4 遍。

这时用**点列表 + 模板**（仍然在普通图元的 `entities` 集合表达式里展开，标注另放 `dimensionEntities`）：

```csharp
// 8 条竖线，y 跨度固定，只有 x 不等距
..new[] { CadDraw.P(-61006.044, -19376.508), CadDraw.P(-60872.044, -19376.508), /* … */ }
    .Select(p => CadDraw.Line(p, CadDraw.P(p.X, p.Y + 262.5), b03)),

// 4 条横线，x 跨度固定，只有 y 不等距
..new[] { CadDraw.P(-62211.487, -19650.554), CadDraw.P(-62211.487, -19906.554), /* … */ }
    .Select(p => CadDraw.Line(p, CadDraw.P(p.X + 300, p.Y), b03)),
```

规则：

- **只对直线**：模板是"锚点 + 固定增量"，一个点列表就能表达；多段线/圆/文字没有单一可变坐标，
  硬套只会更难读；
- 方向先规范化（端点排序），所以正着画、反着画的同一根线能进同一族；
- 增量取**三位小数**分族、按原值输出：同一族的增量必须一致（源图里是精确副本），
  不能拿 `round(dx, 1)` 去近似，否则端点会漂 0.02 mm；
- 成员数 ≥ 3。2 条相同线更像是巧合，写成循环反而增加认知负担；
- 点超过 6 个时按**每行 4 个**折行（`..new[]` 换行 + 花括号块），避免出现 2000+ 字符的单行；
- 与 `EntityArray` **互斥**：先跑等距族，已被阵列吸收的下标不再参与点列表分组；
- 递增顺序按坐标排序输出，便于和源图对照。

实测 04 顶帽图：32 个点列表循环覆盖 268 条线（8 条尺寸界线、7 条尺寸线、7 条 45° 折线、102 条尺寸线斜刻度等），
语句从 1091 降到 **855**；DWG 读回仍是 1633 个实体，逐点覆盖校验 100% 不变——
说明循环只是写法，几何没动。

**为什么不用 `foreach` 语句**：那要把 `entities` 列表拆成"先声明、再 Add"，方法体结构全变；
`.Select` 留在列表表达式里，一句就是一组，和 `EntityArray` 并列，读起来是同一套语法。

**写完必须自检**。用户最容易挑的毛病就是"同 x / 同 y 的怎么还是逐条写的"，
而肉眼很难在几千行里数清楚，所以用脚本判：

```powershell
python scripts/scan_unlooped.py CadCli/Generated/Pier/MyDrawing.cs
```

它跳过 `EntityArray` 块，把剩下的字面量语句按同一套键重新分族，输出每个漏网族的
方法名、图层、方向、步长、成员数、行号；**漏网族必须为 0**，否则说明键、阈值、合并或去重有 bug，
回到第 6~8 步查，不要交付。

```text
Drawing.cs: 未阵列语句 502 条，漏网等距族 0 个，漏网点列表族 0 个
没有漏网的重复族：同 x / 同 y 的等距对象和不等距的同线形都已写成循环。
```

对照实验：同一份 04 桥墩顶帽 JSON，`--strict` 基线（1:1、不阵列）用同一判据扫出 **58 个族**，
优化版扫出 **0 个**——这就是"循环确实做在优化阶段"的证据，也是回退时该看哪一版的分界。

### 9. 圆弧

`Arc` 不单独画，转成顶点 bulge：`bulge = tan(sweep/4)`，`sweep = (ea-sa) mod 2π`（0 取 2π）；
反向走线取负；`|bulge| > 1` 是大于半圆。

### 10. 表格：整段转成 TABLE（含合并单元格）

一张表的图元其实是**一堆线 + 一堆文字**，而且经常画得不规矩：标题行跨列、表头合并、边框画长了一截。
所以不能"看到横竖线就建表"，要按四步走：

**① 找周界闭合的最大子矩形。** 横线按 y、竖线按 x 聚类成候选行列，然后在候选网格里搜
"上边横线、下边横线、左边竖线、右边竖线都被实线覆盖"的最大矩形。表外的引线、尺寸线、
画长了的边框因此被自动排除——这一步决定了边界准不准。

**② 内部缺分隔线 = 合并。** 子矩形内部，如果相邻两格之间没有那条竖线/横线，就说明它们是一个合并单元格。
用并查集把格子连起来，每个连通块就是一个格（1×1 或 k×n）。

**③ 每块必须是矩形，否则整表放弃。** 连通块如果是 L 形、台阶形，`MergeCells` 表达不了，
这时整表退回"线段+文字"并留注释——**宁可不错，也不要画错**。

**④ 吃掉表内线，但把画长的线头还回去。** 表格接管了网格线，可源图的线往往伸出表外一小截，
那部分要按原图层补画成 Line，不能跟着一起消失。

```csharp
var table01 = TableHelper.CreateTable(
    doc, CadDraw.P(4113.343, -16825.014), new string[,]
    {
        { "编号", "直径", "单根长", "根数", "总长", "单位重" },
        { "N1-1", "", "11914", "92", "1096.1", "4.830" },
    },
    [812.5, 812.5, 812.5, 812.5, 812.5, 812.5],   // 列宽
    [571.156, 316.667, 316.667],                   // 行高，自上而下
    125);                                          // 字高
TableHelper.MergeCells(table01, 0, 0, 0, 5);       // 标题行跨 6 列
TableHelper.MergeCells(table01, 1, 1, 2, 1);       // 直径列上下合并

List<Entity> entities = [ table01, /* 其余图元 */ ];
foreach (var table in entities.OfType<TableEntity>())
    table.Layer = b03;                             // TABLE 默认落 0 层
```

落地要点：

- `insertPoint` 取**左上角**，`data[0]` 是最上面一行；行高数组自上而下、列宽数组从左到右，
  数量必须与行列数一致，否则 `CreateTable` 直接抛异常。
- `MergeCells(table, topRow, leftCol, bottomRow, rightCol)` **0 基、含边界**，
  只保留左上角内容，其余格子被清空；**合并区间不能重叠**，否则抛 `InvalidOperationException`。
- 单元格文字按**插入点中心**归属，一格多行时按 y 降序、x 升序拼空格。
- 表格变量必须在 `entities` 列表**之前**声明（要拿引用调 `MergeCells`），再把变量放进列表。
- **空单元格必须真的空着**：`TableHelper` 里已改成空串不写 `CadValue`——
  否则 DwgWriter 会把整张表丢掉（实测 TABLE 变成 0 个实体，文件里只剩 0 实体）。
- 追加模式下目标文件可能没有 `using DwgSharpKit.Tables;`，转换器自动写全限定名。

**仍然要降级的情况**（保持线段+文字，并在方法里留注释）：找不到闭合外框；合并块非矩形。

```csharp
List<Entity> entities =
[
    // 本区域有 17 条横线 / 7 条竖线，但找不到四边闭合的外框，无法确定表格边界 → 保持线段+文字还原
```

### 11. 校验

1. **编译**：`dotnet build` 0 error；
2. **生成 DWG 并读回**：实体总数、类型分布、图层分布、包围盒四项与源图对齐；
3. **几何抽检**：抽长线/大弧比对端点与矢高；源 JSON 的线段集合与生成代码解析出的线段集合做差集，
   差异只应剩"阵列展开的重复项"与已知不还原项。
4. **原生标注**：分列表添加、rotation 分组和尺寸链检查已按顺序完成；展开尺寸链后的
   DIMENSION 数量与源标注数一致（缺字段等跳过项单独计数），逐段保留测量点、定义点、
   rotation、图层、样式、文字覆盖/中心/手动定位标志及尺寸线延长量。

只编译通过 ≠ 还原成功；没做读回比对就不要说"和源图一致"。
