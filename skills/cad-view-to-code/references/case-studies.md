# 案例与回归基线

下列数字来自具体图纸，只作为真实案例和回归参照；新图纸的验收值应以本次 JSON、代码和 DWG 读回结果为准。

## 已跑通的实例（回归基线）

当前仓库里的真实产物（`artifacts/pier/` 是同一张桥墩图的两次工作，各成一个类）：

| | 桥墩 5 分区（旧类） | 当前视图复跑（新类） |
|---|---|---|
| 输入 | `artifacts/pier/legacy-5regions/`（早期人工分区） | `artifacts/pier/shot-01/` + `artifacts/pier/regions/` |
| 来源 | 先前抓的 5 张分区图 | `capture` 当场抓的 1 张截图 |
| 区域 | 5 | 7 候选 → 剔 3 空区 → 4 |
| 源实体 | 2274 | 2831 |
| 生成方法 | 5 | 4 |
| 生成语句 | 1449 → 1382 | 2450 → 1727（含 1 张 TABLE） |
| 去重 | 实体级 196 | 实体级 203、语句级 5 |
| 阵列 | 49 个 / 覆盖 435 实体 | 51 个（横 24 / 纵 27 / 斜 0） |
| 表格 | 无 | 1 张 15×6（区 2），源 76 文字 + 24 线 → 1 实体 |
| 生成 DWG | 1835 实体，四项对齐 | 2141 实体，含 `TableEntity 1`（B-03） |

两个类都在同一个 `.cs` 里：旧类是早期 5 分区（`PierBodyReinforcementDrawingJson`），
新类是当前视口 4 分区（`...Viewport`）。两代人面用的是同一套生成器，所以数值口径一致。

第三个实例是 04 桥墩顶帽钢筋图（8 个视图级分区）：2542 个视图实体 → 834 条语句，
8 个图题用 TitleBlock.Add、89 个 `EntityArray` + 32 个点列表循环（268 条线）、1 张 23×7 的 TABLE（末行合并第 2~6 列），
并段把 1147 条 `Line` 吸收掉 139 条，DWG 读回 1633 个实体；`scan_unlooped.py` 报 0 个漏网族，
同一判据在它的 `--strict` 基线里报 58 个族。交付目录里只有优化版，基线是临时物、用完即删。

表格这条路是实测过的：

- 真实钢筋表：15×6、无合并，76 个单元格文字 + 24 条网格线 → 1 个 TABLE，
  读回 `rows=15 cols=6 merges=0`；
- 合成合并表（标题行跨 3 列 + 末列上下合并）：读回 `merges=2`，
  区间 `(0,0)-(0,2)`、`(1,2)-(2,2)`，标题文字仍在左上角、被覆盖格内容为空 ✓。

多截图命名也跑通过：把同一批 JSON 复制成 `shot-02-*` 后，6 个区域正确生成为
`DrawShot01Region0x` / `DrawShot02Region0x` 六个方法、一个类；再追加 `shot-03-*`，
`--append` 在**原类里**新增 3 个方法（替换 6 个），类数仍是 1。

复跑暴露并已修掉的五个坑：

- 视图边缘的**幻影区域**（有墨迹、0 实体）→ 导出后必须剔除；
- 同一区域的 HRB400 分属两个源图层，一刀切归层会静默改图层；
- 表格**外框常画长一截**（本表横线伸到 x=9800.8，竖线伸到 y=-22483）→
  必须搜"闭合子矩形"而不是取全体包络，多出来的线头要补画回去；
- **空字符串单元格会让 DwgWriter 丢掉整张表**（写出 0 实体）→ `TableHelper` 已改为空值不写内容；
- **图纸被平移后旧 JSON 立即作废**：`check` 命中率从 100% 掉到 0%，
  重跑 `capture→segment→export→detail→check` 后又是 100%。这条是 `check` 存在的理由。

已知偏差：`MText` 的**矩形宽度**未复现（源图带固定宽度框，生成的文字框按实际字宽收缩），
字形与锚点一致但包围盒偏窄；`Solid`、`Defpoints` 的 `Point`、`Hatch`、`Viewport` 不还原；
定义点缺失的标注跳过。
